# ADR 0008: Run Spry's core on Google Cloud as well, and leave sign-in, the report and the parser on AWS

- **Status:** accepted
- **Date:** 2026-11-06
- **Code:** `gcp/` (Terraform, HCP Terraform workspace `meetings-gcp`), `gcp/bootstrap/`,
  `front/firebase.json`, `back/Dockerfile`, `make gcp-*`

## Context

Spry runs on AWS (Labs 2–7): the SPA on S3 + CloudFront, FastAPI in a Lambda container, Aurora
Serverless v2 that pauses when idle, Cognito, a weekly report built by events, and an agenda parser
that calls Claude on Bedrock. The question is what it takes to run the same system on a second cloud,
and what it costs. Only the core has to move: the frontend, the API and the database. The project is
`spry-mykola-2026` in `us-central1`, on the Free Trial credit, with a $5 budget alert.

## Decision: a GCP service for every piece

| Spry on AWS | On Google Cloud | Decision |
| --- | --- | --- |
| S3 + CloudFront (Free plan) + WAF, static frontend | Firebase Hosting | **Replace.** `https://spry-mykola-2026.web.app`, CDN and certificate included. `/api/**` is rewritten to Cloud Run (`front/firebase.json`), so the SPA and the API share one origin and need no CORS, as with CloudFront in Lab 4. |
| Lambda + function URL / API Gateway, FastAPI | Cloud Run | **Replace.** It runs `back/Dockerfile`, the same image as Docker Compose, with no Mangum: uvicorn listens on `$PORT`. Min 0 instances (scales to zero), max 2 (caps the bill and the connections to the database), request-based billing. Public, because the API checks Cognito ID tokens itself. Migrations and the seed run when an instance starts. |
| ECR | Artifact Registry | **Replace.** Repository `meetings-backend`, images tagged with the commit SHA, the last 3 kept (0.5 GB is free). |
| Aurora Serverless v2 (express configuration, IAM sign-in, pauses) | Cloud SQL for PostgreSQL 16, `db-f1-micro`, 10 GB SSD | **Replace.** It does not pause, so it is stopped (`make gcp-db-stop`) whenever nobody is demoing. A fresh database: Alembic migrations + the seed (5 participants), no `pg_dump` from Aurora. Public IP with no authorized networks: only the Cloud SQL connector Cloud Run mounts at `/cloudsql/…` (IAM-checked, encrypted) gets in. |
| DynamoDB | Firestore | **Drop.** Spry never left SQL. |
| Cognito user pool + Google | Identity Platform | **Keep on AWS.** Cloud Run verifies the same Cognito ID tokens; the user pool now also allows the `*.web.app` origin as a redirect URL. Identity Platform is a stretch goal. |
| EventBridge Scheduler | Cloud Scheduler | **Keep on AWS** (the weekly report stays). |
| SQS | Pub/Sub or Cloud Tasks | **Keep on AWS** (the report queue). |
| S3 event → Lambda | Cloud Storage + Eventarc → Cloud Run | **Keep on AWS** (the report mailer). |
| SES | no Google service | **Keep on AWS** (the report mailer). |
| Bedrock (Claude) | Vertex AI | **Keep on AWS.** The browser calls the parser Lambda directly; its CORS allows the `*.web.app` origin too. |
| SSM / Secrets Manager | Secret Manager | **Replace.** One secret, `meetings-db-password`, readable only by the API's service account. |
| CloudWatch Logs | Cloud Logging | **Replace.** Cloud Run sends stdout there; nothing to set up. |
| IAM roles | Service accounts + IAM roles | **Replace.** `terraform@` (only the roles the lab lists plus Firebase Hosting Admin) and `meetings-api@` (Cloud SQL Client, plus Secret Accessor on its one secret). No key exists: Terraform runs as `terraform@` by impersonation with your own `gcloud` sign-in. |
| Terraform `aws` provider, workspace `meetings-dev` | Terraform `google` provider, workspace `meetings-gcp` | **Replace.** A separate configuration and state: one plan cannot break both clouds. Local execution: the state is in HCP Terraform, plan and apply run on the laptop. `gcp/bootstrap/` (local state) creates the service accounts and adds Firebase once. |

The database password is generated by Terraform as an ephemeral value and written only through
write-only arguments (`password_wo`, `secret_data_wo`), so it is neither in the repository nor in the
Terraform state; Cloud Run reads it from Secret Manager as `DB_PASSWORD`.

## The database

| Option | Latency | Bill (nobody using it) | Code |
| --- | --- | --- | --- |
| Cloud SQL around the clock | Same region as the API, < 1 ms per query | ≈ $9.40 a month | none: the same SQLAlchemy models and Alembic migrations, a unix socket instead of a host |
| **Cloud SQL stopped at night / between demos** (chosen) | the same while it runs; ~1 min to start it | ≈ $1.70 stopped, ≈ $3.55 for office hours | none; someone has to start and stop it (`make gcp-db-start` / `gcp-db-stop`) |
| Firestore | single-digit ms, but each screen must be designed as one read | $0 within the daily free quota | a rewrite: meetings ↔ participants is many-to-many, every meeting is filtered by owner, the agenda is JSONB; no joins, no migrations |
| Keep Aurora on AWS, call it across clouds | us-central1 → us-east-1 is ~20–30 ms per round trip, and a request makes several queries | Aurora's ≈ $0.30, plus egress (~$0.09/GB out of AWS) | the express cluster accepts only IAM tokens, so Cloud Run would need AWS credentials (federation from Google to AWS) |

Cloud SQL, stopped when not in use, keeps the code unchanged and costs a few dollars a month of
trial credit. Firestore would make the idle bill $0 but means rewriting the data layer for ~$9 a
month. Calling Aurora across clouds makes every page slower and ties the GCP deployment to AWS.

## E-mail

The weekly report stays on AWS, so it keeps SES: the domain is verified with DKIM and the sender
works. If the report moved to Cloud Scheduler → Cloud Run, it would send through SendGrid (or
Mailgun) over HTTPS, and the API key would be a Secret Manager secret readable only by the report
job's service account, never a plain environment variable or a file in the repository.

## What does not move, and why

- **Sign-in.** Cognito cannot export password hashes, so moving users to Identity Platform means
  every user signs up again or resets the password. Both Cloud Run and Lambda verify the same tokens
  today, so there is no reason to move it until AWS is switched off.
- **The agenda parser.** It is stateless and called straight from the browser, so it works from the
  GCP site unchanged. The trial credit does not pay for Claude on Vertex AI, and Gemini would mean a
  new prompt and a new evaluation of Lab 6's test inputs.
- **The weekly report.** Five AWS services (Scheduler, SQS + DLQ, two Lambdas, S3, SES with DKIM at
  nic.ua) for one e-mail a week. It reads the AWS database, so while both clouds run, it reports on
  AWS's meetings, not GCP's: the two deployments have separate data. That is acceptable for a
  migration state, not for a final architecture.

## Consequences

- The API code did not change. Only `back/Dockerfile` reads `$PORT`. The lock-in sits in the managed
  services around the code (Cognito, SES, Bedrock, EventBridge), not in compute.
- Two deployments, two databases: a meeting created on `web.app` does not appear on
  `app.mykollazab.pp.ua`. Pick one as the live one before telling users about the other.
- Cloud SQL bills by the hour while it runs, whether anyone uses it or not. `make gcp-db-stop` after a
  demo; `make gcp-destroy-plan gcp-apply` when the lab is graded.
- Terraform is applied from a laptop (as `terraform@`). Moving it to Remote execution in HCP Terraform,
  or to GitHub Actions, means Workload Identity Federation for `terraform@`: a pool, an OIDC provider,
  a condition on the numeric repository/workspace IDs. Not done here.
